# 课题1安全可信架构要求 vs ArceOS/tgoskits 成果对照分析

> 依据：《课题1 云边端协同的电力专用物联操作系统体系架构设计方案（中期稿 V0.1）》第 12 章「安全可信架构」  
> 对照对象：tgoskits / ArceOS 生态已实证的架构级安全机制（见 `tgoskits_security_architecture.md`）  
> 覆盖度判定：✅ 已覆盖 · 🟡 部分覆盖 / 有框架待完善 · ⬜ 尚未覆盖（课题可承接方向）  
> 整理日期：2026-07-30

## 一、结论摘要

课题1 把安全定位为「贯穿全栈的横向保障平面」,提出**语言安全 + 组件隔离 + 虚拟化/TEE + 可信启动 + 远程证明 + 动态度量**的全栈设计（第 10 段、12 章）。ArceOS/tgoskits 作为课题端/边侧原型,在**语言与组件安全（12.2）、隔离机制（12.3 前半）** 两项上已有扎实的架构级支撑;在**虚拟化隔离边界**上有框架但存在已知缺口;在**可信执行(TEE)、可信启动、远程证明、动态度量(12.3 后半/12.4/12.5)** 上尚属空白,是课题中后期需重点补齐的部分。

| 课题1 安全能力（12 章） | ArceOS/tgoskits 成果 | 覆盖度 |
|--------------------------|----------------------|--------|
| 12.2 语言与组件安全 | Rust 所有权/类型系统 + unsafe 集中封装(`ax_memory_addr` 强类型、`GuestMemoryAccessor`) | ✅ |
| 12.3 进程/容器/VM 多级隔离 | 地址空间隔离 `axaddrspace`、二级页表、seccomp/capabilities/namespace | 🟡 |
| 12.3 分区/TEE 隔离 | 无 TEE 支持 | ⬜ |
| 12.3 动态划分隔离域 | 静态隔离为主,无按可信等级动态划域 | ⬜ |
| 12.3 跨域共享内存显式权限+完整性校验 | 受控内存访问器有边界契约,但无完整性(度量)校验 | 🟡 |
| 12.3 远程证明 | 无 | ⬜ |
| 12.4 可信启动（逐级验签/回滚/撤销） | 无（tgoskits 反有未修的启动信任缺口 #1749/#1763） | ⬜ |
| 12.5 动态安全与恢复（运行期度量/降级/隔离） | 有 panic backtrace/memtrack/lockdep 可观测,无可信度驱动的动态响应 | 🟡 |

## 二、逐项对照

### 12.2 语言与组件安全

**课题要求**：课题要求：安全敏感组件优先 Rust,利用所有权/借用/生命周期/类型系统减少 UAF/双重释放/悬空指针/数据竞争;unsafe/C 硬件访问集中封装成可审计最小边界。

**覆盖度**：✅ 已覆盖（原型级已达成）

- 整个 ArceOS/Starry/axvm 栈以 Rust `#![no_std]` 编写,天然消除课题所列内存/并发缺陷类别。
- **强类型地址** `GuestPhysAddr`/`PhysAddr`(`ax_memory_addr`)编译期阻止 GPA/HPA 混用——正是「类型系统减少缺陷」的直接体现。
- **unsafe 集中封装**：`GuestMemoryAccessor` trait 把裸内存访问收敛为「返回 (HPA, 可访问字节数) 的受控接口」,即课题要求的「可审计最小边界」。axvisor KVM 后端的 C/Rust ABI 边界(slot-first fault-in)也遵循此原则。
- 已合并的 UAF/溢出修复(#920/#1120)与 lockdep 锁安全(`ax-kspin` #1397)佐证该机制在实践中生效。

### 12.3 隔离与可信执行 —— 隔离部分

**课题要求**：课题要求：进程/容器/VM/分区/TEE 多级隔离;按可信等级动态划分隔离域;跨域共享内存/设备/核间通信显式权限+完整性校验。

**覆盖度**：🟡 部分覆盖

- **进程/容器隔离 ✅**：Starry 实现 seccomp、capabilities、`PR_SET_NO_NEW_PRIVS`、namespace/cgroup(#1275/#810/#1031/#1642),对齐 Linux 隔离原语。
- **VM 隔离 🟡**：axvm 提供 guest 二级页表(NPT/stage-2)地址空间隔离 + OS-neutral vCPU 后端,但存在**已知虚拟化边界缺口**——issue #1730(中断号越界写宿主)、#1734(GPA 当 HPA 解引用)、#1745(`todo!` 触发 hypervisor panic),对应课题威胁模型中的「虚拟化逃逸」,需优先修复。
- **分区/TEE ⬜**：暂无分区管理程序(partitioning hypervisor)与 TEE(如 TrustZone/SGX/RISC-V PMP-based)集成。
- **动态划域 ⬜**：当前为静态隔离配置,无「按业务关键性/可信等级动态划分隔离域」能力。
- **跨域共享内存 🟡**：`GuestMemoryAccessor` 提供了显式权限边界(可访问字节数、RDONLY 标志),但缺少课题要求的「完整性校验」(如共享内存度量/MAC)。

### 12.3 隔离与可信执行 —— 可信执行/远程证明部分

**课题要求**：课题要求：通过远程证明向云/边证明节点启动链与运行状态。

**覆盖度**：⬜ 尚未覆盖

- ArceOS/tgoskits 目前无远程证明(Remote Attestation)机制,无度量根(RoT)、无证明报告生成/验证链路。此项依赖 TEE 或 TPM/度量启动基础,属课题需从架构补齐的能力。

### 12.4 可信启动

**课题要求**：课题要求：对固件/引导/内核/运行时/关键应用逐级验签;更新包签名、版本依赖、灰度、回滚、证书撤销、紧急修复。

**覆盖度**：⬜ 尚未覆盖（且现状有反向缺口）

- tgoskits 无可信启动链实现。
- 反而存在**启动/供应链信任缺口**：issue #1749(串口选择的 HTTP 内核无真实性校验)、#1763(Fork PR 在自托管 Runner 执行代码)、#1756/#1758/#1759(以 root 装未认证 APK / 执行未固定上游分支)——恰是课题 12.4「更新包必须签名」的反面案例,可作为课题启动/更新安全的现实驱动。

### 12.5 动态安全与恢复

**课题要求**：课题要求：运行期持续采集完整性/访问/通信/资源异常;可信度下降时减少可访问服务、迁移敏感任务、隔离异常设备或切换恢复镜像。

**覆盖度**：🟡 部分覆盖（仅可观测,无闭环响应）

- **可观测基础 🟡**：有 panic backtrace hook(`axbacktrace` #1653)、memtrack 分配回溯(#1020)、lockdep 运行期锁检测——提供了「异常采集」的部分能力。
- 越界 hart 受控 park(#919)、guest 缺页受控恢复(#788/#883)体现了「受控降级而非崩溃」的思路,与 12.5「切换恢复」方向一致。
- **闭环响应 ⬜**：缺少课题要求的「可信度评估 → 服务降级/任务迁移/设备隔离」的动态安全策略引擎,当前无运行期完整性度量与可信度模型。

## 三、对照威胁模型（12.1）的成果映射

| 课题威胁（12.1） | ArceOS/tgoskits 相关成果 | 状态 |
|------------------|--------------------------|------|
| 内存与并发缺陷 | Rust 类型系统 + `ax-kspin` lockdep + UAF/溢出修复(#920/#1120)+ 栈 guard page(#811) | ✅ 有力覆盖 |

## 四、汇报建议（成果定位与后续着力点）

1. **可作为中期已达成成果汇报的**：语言与组件安全(12.2)、进程/容器隔离与 Linux 兼容权限模型(12.3 部分)、内存/并发安全机制——这几项在 ArceOS/tgoskits 原型上已有架构级、可测试、已合并的实证支撑,与课题「Rust 语言安全 + 组件隔离」主张高度吻合。
2. **中期「有框架、待完善」应如实说明的**：虚拟化隔离边界已有二级页表/OS-neutral vCPU 框架,但存在 #1730/#1734/#1745 三项高/中危虚拟化逃逸缺口——建议列为下一阶段第一优先,直接对应 12.1「虚拟化逃逸」与 12.3「VM 隔离」。
3. **中后期需从架构新增的**：TEE/分区隔离、可信启动链、远程证明、动态度量与可信度驱动的安全响应(12.3 后半/12.4/12.5)——这些是课题全栈可信设计的关键拼图,原型目前基本空白,应在计划中明确承接路径(如引入 RISC-V PMP/TrustZone、度量启动、attestation 协议)。
4. **可信 I/O 是电力物联特色需求**：课题 12.1 专门点名「异构外设和 AI 加速器可信 I/O」,而 tgoskits 的 NPU/VPU 驱动恰有信任用户指针/DMA 地址的缺口(#1732/#1739/#1762)——这是课题安全增强最具场景针对性的着力点,建议重点立项。
