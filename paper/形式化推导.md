# 形式化推导稿：从第一性原理推导 Hypervisor↔OS 接口契约

> 本文档是论文新增"形式化"一节的推导底稿。目标：不把七组接口当作工程直觉的产物，而是从
> Popek-Goldberg 虚拟化定理的三性质出发，经过"资源识别 → 能力推导 → Rely-Guarantee 契约化"，
> 推出契约的**充分性**、**最小性**与**可移植性**三条命题。语义主框架为 Rely-Guarantee。
> 定义/引理/定理均给出纸面证明骨架（proof sketch），不做机械化证明。

---

## 0. 记号与出发点

### 0.1 为什么从 Popek-Goldberg 出发

Popek 与 Goldberg（1974）\[PG74\] 给出了"一个体系结构可被高效虚拟化"的充分条件，其模型把处理器状态刻画为
`S = (E, M, P, R)`——其中 `M` 为执行模式（system/user）、`P` 为程序计数器、`R = (l, b)` 为**内存重定位-边界寄存器**（把表观地址映射到绝对地址）。它把指令分为特权（privileged）、敏感（sensitive = control-sensitive ∪ behavior-sensitive）、无害（innocuous），并证明：

> **PG 定理**：若敏感指令集 ⊆ 特权指令集，则可构造满足三性质的 VMM。

三性质为：**等价性（Equivalence）**——guest 在 VM 内外行为本质一致；**资源控制（Resource Control）**——VMM 完全掌控被虚拟资源；**效率（Efficiency）**——绝大多数指令由硬件直接执行。

**关键观察（本节全部推导的支点）**：PG 的三性质并非"CPU/ISA 独有"。它们是"一个中介（mediator）把资源交给不受信任的 guest 使用"时**普遍成立**的正确性约束。PG 只在**处理器状态 + 单一内存重定位寄存器 R** 这一狭窄资源上实例化了三性质，并显式声明**省略 I/O 与中断**。本文的第一性原理推导，就是把 PG 三性质从"ISA 层的 R 寄存器"**提升（lift）到"OS 服务层的全部被虚拟资源"**，再问：维持三性质，OS 至少必须向核心提供哪些能力。

### 0.2 状态与关系记号（Rely-Guarantee 语义）

我们采用 Rely-Guarantee \[Jones83\] 的两关系刻画。系统全局状态记为 `Σ`，分解为：

- `Σ_g`：guest 可见状态（guest 寄存器、guest 物理内存内容、guest 视角的设备/中断状态）。
- `Σ_h`：host/核心私有状态（vCPU 影子结构、stage-2 页表、契约簿记）。
- `Σ_o`：底座 OS 私有状态（OS 的物理内存所有权、调度队列、IRQ 框架、IOMMU 表）。

一个组件用一对状态二元关系刻画：**Rely `R ⊆ Σ × Σ`**（该组件*假设*环境的每个原子步满足的关系）与 **Guarantee `G ⊆ Σ × Σ`**（该组件*承诺*自身每个原子步满足的关系）。并行组合的核心规则（本文可移植性判据的来源）为：

> **R-G 并行组合规则**：组件 A、B 并行运行时，若 `G_A ⇒ R_B` 且 `G_B ⇒ R_A`，则组合系统的 rely/guarantee 可合成，且各组件在其 rely 下证明的性质在组合中保持。

我们的三个角色：**Core（可移植虚拟化核心）**、**OS（某个底座的适配层 + 底座本体）**、**Guest**。契约 `𝒞` 就是"Core 对 OS 的 Rely"与"OS 对 Core 的 Guarantee"的交汇。

## 1. 第一步：资源识别（把 PG 的 R 推广为资源族）

PG 只形式化了两类被虚拟资源：处理器执行状态（`M, P`）与内存重定位（`R`）。虚拟化一个完整平台，需要中介的资源远不止此。Penneman 等（2013）\[Pen13\] 已证明 PG 的原始模型必须补入**分页虚拟内存、中断、I/O** 才能刻画现代（ARM）体系结构。据此我们把"被虚拟资源"补全为资源族 `𝓡`：

| 资源 | PG 中的对应 | 说明 |
|------|------------|------|
| `R₁` 物理内存与地址翻译 | `R = (l,b)` 的推广 | 单寄存器重定位 → 两级/stage-2 页表 |
| `R₂` 执行上下文 | `M, P` 的推广 | 单核处理器状态 → 多 vCPU |
| `R₃` 中断 | （PG 省略） | 中断的接收、屏蔽、注入 |
| `R₄` 时间 | （PG 省略） | 定时器/时钟源 |
| `R₅` 设备与 MMIO | （PG 省略） | 内存映射 I/O、端口 I/O |
| `R₆` DMA 可见性 | （PG 省略） | 设备对 guest 内存的访问范围 |

**定义 1（被虚拟资源）**：一个被虚拟资源 `Rᵢ` 是一个状态投影 `πᵢ : Σ → Σ|ᵢ`，配一组 guest 可发起、其效果落在 `Σ|ᵢ` 上的操作。Guest 只能通过这些操作触碰 `Rᵢ`。

> **说明**：`R₃–R₆` 正是 PG 显式排除的部分，也是"为什么 PG 不足以刻画 hypervisor 对 OS 的依赖"的根源——现代虚拟化的资源控制责任大量落在中断与 I/O 上。

## 2. 第二步：能力推导（从资源控制性质推出最小操作集）

这是把"接口"从直觉变成推导的核心一步。对每个资源 `Rᵢ`，我们问：**要让 Core 对 `Rᵢ` 维持 PG 的资源控制 + 等价性，Core 必须能够原子地施加哪些操作？** 而 Core 自身运行在 OS 之上、不拥有底层特权资源，因此这些操作**必须由 OS 通过契约提供**。

我们把资源控制形式化为一个不变式，再由"维持该不变式所需的最小操作闭包"反推能力集。

**定义 2（资源控制不变式 RC-Inv）**：对资源 `Rᵢ`，`RC-Invᵢ` 断言：guest 对 `Rᵢ` 的任何操作，其可观测效果都落在 Core 当前授权的范围内，且 Core 能在任意时刻收回或重定向该授权。

### 2.1 以 R₁（内存）为完整范例

**命题（R₁ 的最小能力）**：维持 `RC-Inv₁` 与等价性，当且仅当 Core 可经由契约施加以下操作：
`alloc_phys`（取得可控物理帧）、`map_stage2`（建立 GPA→HPA 映射及权限）、`unmap_stage2`（撤销映射）、`flush_tlb`（使旧翻译失效）。

**证明骨架**：
- （充分）给定这四个操作，Core 可在 guest 启动前为其物理地址空间建立全部 GPA→HPA 映射（`alloc_phys`+`map_stage2`），从而 guest 每次访存都被 stage-2 约束在授权范围内——`RC-Inv₁` 成立；等价性成立，因为 guest 看到连续的 guest-physical 空间与真实硬件无异。收回授权时 `unmap_stage2`+`flush_tlb` 保证旧映射不再可用。
- （必要）逐一反证：
  - 去掉 `map_stage2`：Core 无法建立任何 GPA→HPA 授权，guest 要么无内存（违反等价），要么直接访问 host 物理内存（违反资源控制）。
  - 去掉 `unmap_stage2`：授权一旦建立不可收回，存在"guest 释放后仍可访问"的 guest 行为使 `RC-Inv₁` 被破坏。
  - 去掉 `flush_tlb`：`unmap` 的效果不保证对硬件翻译缓存生效，存在一条 guest 访存经陈旧 TLB 命中已撤销映射，破坏资源控制。
  - 去掉 `alloc_phys`：Core 无法获得"自己有权支配"的帧，任何 `map_stage2` 的源帧所有权未定，`RC-Inv₁` 无法建立。
  ∎（骨架）

### 2.2 其余资源的能力推导（同法，列出结论）

对 `R₂–R₆` 施加相同的"RC-Inv 最小闭包"论证，得：

| 资源 | 维持 RC-Inv + 等价性所需最小能力 | 对应契约操作 |
|------|-------------------------------|-------------|
| `R₁` 内存 | 建立/撤销/使失效 GPA→HPA 授权 | `alloc_phys, map_stage2, unmap_stage2, flush_tlb` |
| `R₂` vCPU | 创建执行上下文、进入降权 guest 直至陷入、读写 guest 寄存器、销毁 | `vcpu_create, vcpu_run, vcpu_get/set_regs, vcpu_destroy` |
| `R₃` 中断 | 绑定物理中断到 Core 回调、向 vCPU 注入虚拟中断、EOI | `irq_register, irq_inject, irq_eoi` |
| `R₄` 时间 | 装备定时器以夺回控制（调度配额/看门狗） | `timer_arm` |
| `R₅` 设备/MMIO | 物理 MMIO 读写、注册 guest MMIO 陷入回调 | `mmio_read/write, register_mmio_handler` |
| `R₆` DMA | 约束设备对 guest 内存的可见性（可选，取决于 IOMMU） | `iommu_map/unmap, iommu_attach_device` |

此外，两类**非资源型**能力从"Core 需被启动并被观测"这一元需求推出：**生命周期**（`init, query_platform`）与**日志**（`log`）。它们不承担资源控制，但为契约提供控制权移交点。

**推论（七服务组的必然性）**：`R₁–R₆` 加生命周期/日志，恰好聚成七个服务组——即论文 Table I。**七组不是设计选择，而是"PG 三性质 × 完整资源族"的推导结果。**

> **vcpu_run 与 PG 的直接对应**：PG 的 trap-and-emulate 要求"敏感操作陷入 VMM"。在 OS 服务层，这一"陷入并回到 Core"的语义正是 `vcpu_run` 的规约：它必须*阻塞直至 guest 陷入*，把控制交还 Core。这是 PG 公理在契约中的落点。

## 3. 第三步：契约的 Rely-Guarantee 形式化

现在把上面推出的能力集包装成形式契约。

**定义 3（底座契约 𝒞）**：契约 `𝒞 = (Ops, Gᴼˢ, Rᶜᵒʳᵉ)`，其中：
- `Ops` 是第二步推出的操作集合（七组）。
- 对每个操作 `op ∈ Ops`，给出其**操作规约** `⟨pre_op, post_op⟩`（前置/后置断言，Design-by-Contract 风格 \[Meyer\]），刻画 op 对 `Σ_o`/`Σ_h` 的原子效果。例：
  `post_{map_stage2}(gpa, hpa, perm)`：此后 guest 对 `gpa` 的访问以权限 `perm` 落到 `hpa`，直到对应 `unmap_stage2`。
- `Gᴼˢ`（OS 的 Guarantee）：OS 承诺其每个原子步要么是某个 `op` 的正确实现（满足其规约），要么不触碰 Core 授权范围内的 `Σ_h/Σ_g`（即 OS 不擅自改动 guest 内存/vCPU 状态）。
- `Rᶜᵒʳᵉ`（Core 的 Rely）：`Rᶜᵒʳᵉ := Gᴼˢ`。即 Core 假设"环境（OS）的每一步都符合 OS 的 Guarantee"。

**定义 4（Core 的 Guarantee）**：`Gᶜᵒʳᵉ` 断言 Core 每个原子步维持 PG 三性质在资源族 `𝓡` 上的提升版本：对所有 `Rᵢ`，`RC-Invᵢ` 保持，且 guest 可观测行为与"直接在真实平台上运行"等价（Equivalence-Inv）。

> 至此，"契约"被精确定义为一对关系 `(Rᶜᵒʳᵉ, Gᶜᵒʳᵉ)` 加上 OS 侧的镜像 `(Rᴼˢ, Gᴼˢ)`，其中 `Rᶜᵒʳᵉ = Gᴼˢ`。KVM 兼容 ABI 是 Core 对 **Guest** 的 Guarantee 的一个具体投影，方向相反（Core 是 provider），此处不展开。

## 4. 三个命题及证明骨架

### 定理 1（契约充分性 / Soundness）

> 若某底座 OS 的适配层满足 `Gᴼˢ`（即其每个契约操作实现满足对应 `⟨pre,post⟩`，且不擅动授权状态），则 Core 在该底座上维持 PG 三性质的提升版本，即 `Gᶜᵒʳᵉ` 成立。

**证明骨架**：Core 的正确性证明是在"环境步满足 `Rᶜᵒʳᵉ`"这一假设下做的 R-G 推理。由 `Rᶜᵒʳᵉ := Gᴼˢ`，只要 OS 实现满足 `Gᴼˢ`，则 Core 证明中用到的每个环境假设都被兑现。对 Core 的每个动作按其控制/资源类别归约到 PG：内存动作维持 `RC-Inv₁`（§2.1），vCPU/中断/时间/设备动作维持各自 `RC-Invᵢ`（§2.2）；`vcpu_run` 的"陷入即返回"规约保证敏感操作不被 guest 私自完成（对应 PG 的 `S ⊆ P`）。逐类归纳，`Gᶜᵒʳᵉ` 在所有可达状态保持。∎（骨架）

### 定理 2（契约最小性 / Minimality）

> 对 `Ops` 中每个操作 `op`，存在一个 guest 行为与一条执行，使得移除 `op`（或其规约中的某关键后置条件）后，`RC-Inv` 或 Equivalence-Inv 被破坏。因此 `Ops` 中无冗余操作。

**证明骨架**：§2.1 已对 `R₁` 的四个操作各给出一条破坏执行（去 `map_stage2`/`unmap_stage2`/`flush_tlb`/`alloc_phys` 分别对应一类反例）。对 `R₂–R₅` 同法构造：例如去 `irq_inject`，则存在一个依赖外部中断唤醒的 guest 永久阻塞，违反 Equivalence；去 `register_mmio_handler`，则 guest 对模拟设备的 MMIO 要么直通真实设备（违反资源控制）要么无响应（违反等价）；去 `timer_arm`，则 Core 无法从死循环 guest 夺回 CPU，违反资源控制。`R₆` 为可选组，其缺失不破坏核心不变式，只收缩可支持特性集（passthrough），与"可选能力"的设计一致——这本身也是最小性论证的一部分：`R₆` 不在**必需**闭包内。∎（骨架）

> **注**：最小性是相对"维持 PG 三性质"这一目标而言的最小，不是绝对最小 API。热迁移、快照、CPU 亲和等是**在三性质之上的额外性质**，其对应操作不在此闭包内——这正解释了论文 Discussion 中"契约充分但不完备"的表述。

### 定理 3（底座可移植性 / Portability）

> 设 Core 已被证明为抽象规约 `Spec` 的精化：`Core ⊑ Spec`，且该证明仅依赖 `Rᶜᵒʳᵉ`。则对任意两个满足 `Gᴼˢ` 的底座实现 `I₁, I₂`（如 ArceOS、Asterinas、Linux 适配层），`Core ⊑ Spec` 在 `I₁` 与 `I₂` 下同时成立，且 guest 可观测行为不变。

**证明骨架**：由 R-G 并行组合规则，`Core ∥ Iⱼ` 的组合要求 `G_{Iⱼ} ⇒ Rᶜᵒʳᵉ` 且 `Gᶜᵒʳᵉ ⇒ R_{Iⱼ}`。前者即 "Iⱼ 满足 `Gᴼˢ`"（前提），后者由定义 4 与 OS 适配层只依赖 Core 不擅动 guest 状态给出。因 Core 的精化证明只引用 `Rᶜᵒʳᵉ`（不引用任何 `Iⱼ` 的私有状态 `Σ_o`），该证明对 `I₁, I₂` 是**参数化**的：替换实现不改变证明中任何一步。故 `Core ⊑ Spec` 在两实现下同为定理。Guest 可观测行为由 `Gᶜᵒʳᵉ` 的 Equivalence-Inv 固定，与 `j` 无关。∎（骨架）

> **这是论文核心论点的形式表述**：substrate-OS portability = "Core 对同一抽象规约的精化，在多个满足契约 Guarantee 的 OS 实现下参数化地成立"。它把"同一核心跑在三 OS 上"从工程观察升格为可证明命题。

## 5. 与相关形式化工作的定位

- **对 PG74 的关系**：我们不修改 PG 定理，而是把其三性质从 ISA 层**提升**到 OS 服务层，并补入 PG 显式省略的中断/时间/设备/DMA（承接 Penneman13 的扩展精神）。
- **对 seL4 / CertiKOS 的关系**：借用其 refinement 机制表述可移植性（定理 3）。特别是 CertiKOS 的 **certified abstraction layer**（underlay/overlay 双接口）与我们"Core 的 Rely（对 OS 的 underlay 依赖）+ Core 的 Guarantee（对 guest 的 overlay）"结构同构。
- **对 SeKVM/HypSec 的关系**：它的 **KCore/KServ 拆分**（把宿主 OS 当作行为受约束的下层）是本契约"OS 作为受 `Gᴼˢ` 约束的 Rely 环境"最贴切的工程先例；差异在于其目标是隔离性证明（固定 Linux），我们的目标是可移植性推导（参数化多 OS）。
- **对 Rely-Guarantee / interface automata 的关系**：R-G 提供并发共享状态下的 assume/guarantee 语义主框架；interface automata 可作为补充，刻画调用**时序协议**（如 `init` 必先于 `vcpu_run`），这是 R-G 状态关系不直接表达的一层，留作契约的协议侧扩展。

## 6. 待定与风险（写作前需确认）

1. **`Spec` 的具体形态**：定理 3 依赖一个抽象规约 `Spec`。需决定它写到多细（vCPU 状态机 + stage-2 抽象即可，还是要含 KVM ABI 语义）。建议先只覆盖 §2 的资源不变式层面，够支撑定理即可。
2. **纸面证明的严谨度**：当前为 proof sketch。投 OSDI/SOSP 级别需要把定义 2/定义 4 的不变式写成可陈述的逻辑公式；投偏系统的会议，sketch + 一个完整展开的范例（R₁）通常够。
3. **是否机械化**：用户已定为"纸面证明"，此稿不含 Coq/Isabelle。若审稿要求，`Core ⊑ Spec` 的参数化论证最适合先机械化。
4. **KVM ABI 侧的对称形式化**：本稿聚焦 substrate 侧。guest 侧（Core 作为 provider 对 guest 的 Guarantee）可另起一小节对称处理，暂未展开。
