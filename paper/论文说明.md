# 论文中文说明稿

**标题**：《Decoupling Hypervisors from Substrate Operating Systems: An Interface-Contract Approach to OS-Portable Virtualization》
（《将 Hypervisor 与底层操作系统解耦：一种面向 OS 可移植虚拟化的接口契约方法》）

**核心主张**：Hypervisor 与宿主 OS 的紧耦合本质上是一个"软件架构问题"，而非虚拟化的本质需求。只要定义一份"窄而语义忠实"的**底层接口契约（substrate interface contract）**，同一个虚拟化核心就能跑在多个截然不同的 OS 上。论文以 AxVisor 为载体，让它同时运行在 ArceOS、Asterinas、Linux 三种底座上，并对外暴露 KVM 兼容 ABI 让 guest 侧也解耦。

本文件逐部分说明论文各章节写了什么，与 `paper/` 下的 tex 源码一一对应。

---

## Abstract（摘要）

对应 `sections/abstract.tex`

点明问题：KVM 绑死 Linux、Bao/Jailhouse 假设特定启动与设备模型、DuVisor 也绑死单一内核。这导致每个新 OS 想要虚拟化，要么从零重写 hypervisor，要么大动内核手术。

给出方案：把 AxVisor 围绕一份显式的"底层接口契约"重构，让虚拟化核心与 OS 专有服务分离；核心跑在三种底座上，每种底座只贡献一层薄薄的适配层；再用 KVM 兼容 ABI 解耦 guest 侧。

给出验证：在 Asterinas 和 Linux 两种底座上启动裸机 Linux guest；用接口规模、代码复用率、虚拟化开销三类指标量化"可移植成本"。结论是——可移植性用很窄的契约 + 少量适配代码就能实现。

## I. Background and Motivation（背景与动机）

对应 `sections/introduction.tex`，PDF 第一节，分四个小节。

- **A. 耦合是架构问题**：Hypervisor 必须依赖底座来分配内存、管理执行上下文、路由中断、访问设备、协调初始化。逐一分析现有系统的耦合：KVM 是 Linux 子系统（`/dev/kvm` + ioctl）；Firecracker 建在 KVM 上，间接继承依赖；Bao/Jailhouse 虽 TCB 小但仍绑底座；ACRN 绑 service-VM；DuVisor、Out-of-Hypervisor 只是把耦合"搬家"而非消除。结论：虚拟化支持不是可移植能力，而是"每个 OS 都要重新投资"。

- **B. 解耦的两个维度**：已有研究关注 guest 可移植性、硬件（ISA）可移植性；而**第三个维度——底座 OS 可移植性**基本没人碰。进一步指出可移植性有两个独立的侧面：**substrate-facing side**（hypervisor 如何向下获取 OS 服务）和 **guest-facing side**（guest 如何向上与 hypervisor 交互）。只解耦一侧都不够，本文两侧同时做。

- **C. 软件工程视角**：这是"把可复用组件通过显式最小契约与平台服务分离"这一经典问题的实例。难点在于——契约太窄则功能不够，太贴合某个 OS 则失去可移植，掩盖语义差异则"假可移植"。所以契约必须小、显式、且忠实于虚拟化真正需要的语义。

- **D. 为什么是现在**：一批用内存安全语言、非传统架构写的新 OS 正在涌现（Asterinas 的 framekernel、Unikraft/LibrettOS 等 library-OS/unikernel）。它们都需要虚拟化但不该从零造轮子——这正是本文要填的空白。

## II. Design（设计）

对应 `sections/design.tex`，PDF 第二节，含 **表 I**（契约的服务组）。

- **A. 设计目标与原则**：四个目标 G1~G4——G1 底座可移植（用"适配层多小"来度量）、G2 最小且忠实的契约、G3 guest 侧中立、G4 有界的适配成本。三条原则：虚拟化逻辑与 OS 服务分离、显式优于隐式、按能力签约（capability-based）。

- **B. 架构总览**（对应图 Fig.1）：三层结构——顶层 guest VM 通过 KVM ABI 交互；中层可移植核心（vCPU 生命周期、stage-2/EPT 内存管理、trap 分发、hypercall、虚拟设备、VM 生命周期）；底层针对具体 OS 的适配层。核心只调用契约，适配层才调用 OS 原生 API。两条独立的"缝"：核心/适配层之间、guest/核心之间（KVM ABI）。

- **C. 底层接口契约**（论文核心，表 I 总结）：把契约拆成七个服务组，逐组说明——
  1. **内存**：`alloc_phys`、`map_stage2`、`unmap_stage2`、`flush_tlb`（语义压力最大）
  2. **CPU/vCPU**：`vcpu_create`、`vcpu_run`、`vcpu_get/set_regs`、`vcpu_destroy`
  3. **中断/定时器**：`irq_register`、`irq_inject`、`irq_eoi`、`timer_arm`（语义分歧最大）
  4. **同步**：自旋锁 + 最小内存屏障（要求能在中断上下文使用）
  5. **设备/MMIO**：`mmio_read/write`、`io_port`、`register_mmio_handler`
  6. **DMA/IOMMU**：`iommu_map/unmap`、`iommu_attach_device`（可选能力，缺失则优雅降级）
  7. **生命周期与日志**：`init`、`query_platform`、`log`

- **D. KVM 兼容 ABI**：核心内实现一个 KVM-ABI shim，把标准 KVM ioctl（`KVM_CREATE_VM`、`KVM_CREATE_VCPU`、`KVM_RUN` 等）翻译成契约调用。强调一个**故意的非对称**：底座侧契约是"提供者接口"（每个 OS 实现），guest 侧 KVM ABI 是"消费者接口"（核心实现给 guest 用）。这个双重解耦让 guest×substrate 矩阵无需 O(g×s) 的工作量。

## III. Implementation（实现）

对应 `sections/implementation.tex`，PDF 第三节，含 **表 II**（实现汇总）。

- **A. 核心重构**：原 AxVisor 把虚拟化逻辑与 ArceOS 调用交织在一起。做**依赖倒置重构**——把契约定义成一个 Rust trait object，核心通过引用持有；所有对 ArceOS 的直接调用改为经 trait 调用。重构后核心不含任何 OS 专有符号。

- **B. 三个适配层**（覆盖 OS 设计空间三个点）：
  - **ArceOS（unikernel）**：最直接，大多数契约操作只需轻包装，作为 baseline。
  - **Asterinas（framekernel）**：需调和三处语义不匹配——物理内存（从安全抽象里"恢复"物理帧号）、执行上下文（vcpu_run 建在 Asterinas 线程上）、中断（在其框架内注册契约 handler）。核心逻辑零改动。
  - **Linux（monolithic）**：作为"压力测试"，以内核模块实现。需要显式"逃离"Linux 抽象：用连续帧分配器、自行管理 EPT/NPT（与宿主 KVM 共存不冲突）、桥接 IRQ 子系统并注意上下文语义、内核线程进 VMX root/EL2。结论：Linux 能提供全部能力，但每项都要绕开应用层从不碰的抽象——这恰恰说明为什么需要"hypervisor 级契约"而非通用 OS API。

- **C. KVM-ABI Shim**：位于核心内，实现标准 ioctl 面。因为 shim 是 OS 中立的，同一 guest 镜像 + 同一 VMM 逻辑能在三种底座上跑。

## IV. Evaluation（评估）

对应 `sections/evaluation.tex`，PDF 第四节，含 **表 III~VI** 和四个研究问题。

- **四个 RQ**：RQ1 可移植成本、RQ2 功能性、RQ3 guest 侧中立性、RQ4 开销。
- **A. 实验设置**：三底座、裸机 Linux guest、baseline 是重构前的 AxVisor-on-ArceOS、参考系是原生 KVM。
- **B. RQ1（表 III）**：度量各适配层代码量与核心复用率；并把每个契约操作按适配方式分类为 **direct mapping / bridging / recovery**，发现"可移植成本不均匀，集中在内存和中断"——这本身就是发现。
- **C. RQ2（表 IV）**：功能矩阵。关键结果——同一 guest 镜像在 Asterinas 和 Linux 上都能启动。
- **D. RQ3（表 V）**：用完全相同的 guest 镜像/配置/VMM 序列跨底座验证，证明"底座选择在核心之上不可见"。
- **E. RQ4（表 VI）**：四类指标——VM 生命周期、trap 处理往返延迟、内存操作、I/O 路径。预期：trap 处理（在共享核心里）接近 baseline，开销集中在适配层桥接。
- **F. 有效性威胁**：三个底座不能穷尽 OS 设计空间；guest workload 单一；与原生 KVM 比较存在成熟度不对称。

## V. Related Work（相关工作）

对应 `sections/related_work.tex`，PDF 第五节，分三类：

- **Hypervisor 架构及其底座耦合**：Xen、KVM、Firecracker、Bao、Jailhouse、ACRN、DuVisor、Out-of-Hypervisor——逐一说明它们如何耦合，以及 AxVisor 的差异（把依赖变成显式最小契约）。
- **OS 模块化 / library OS / unikernel**：Unikraft、LibrettOS、Asterinas 等证明 OS 服务可模块化；AxVisor 从"消费者侧"应用同一原则。
- **guest 侧标准化与硬件可移植性**：KVM ABI 本身是 guest 侧解耦；硬件可移植（Arm/RISC-V）与底座可移植正交、互补。

## VI. Discussion（讨论）

对应 `sections/discussion.tex`，PDF 第六节：

- **A. 契约揭示了什么**：契约同时是"诊断工具"——内存和中断在所有底座上都最费桥接/恢复，说明契约结构本身识别了 OS 分歧点。契约也是"什么样的 OS 是好 hypervisor 底座"的规格说明。
- **B. 当前契约的局限**：passthrough 受 IOMMU 可选能力限制；vCPU 放置由底座调度器决定；热迁移/快照/嵌套虚拟化超出范围。这些是自然扩展而非反驳。
- **C. 三底座之外的普适性**：已覆盖 unikernel/framekernel/monolithic；microkernel/capability-based（如 seL4）留作未来工作。
- **D. 对 OS 与 hypervisor 协同设计的启示**：把适配层当成"写驱动"一样的有界工程任务；把 O(OSes×guests) 矩阵降到 O(OSes)+O(guests)。

---

## VII. Conclusion（结论）

对应 `sections/conclusion.tex`，PDF 第七节：重申"hypervisor-OS 耦合主要是软件架构问题"，通过底座接口契约可以解决；同一核心跑在三底座上 + KVM ABI 保持 guest 侧解耦；裸机 Linux guest 双底座启动证明契约足够。更大的启示：hypervisor 无需绑死单一 OS，可作为可移植系统组件被重定向。
